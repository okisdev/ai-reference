## Context

Dev script: !`jq -r '.scripts.dev // "(none)"' package.json 2>/dev/null || echo "(none)"`

Framework marker: !`if find . -maxdepth 1 -name 'next.config.*' -print -quit | grep -q .; then echo "next.config"; elif find . -maxdepth 1 -name 'vite.config.*' -print -quit | grep -q .; then echo "vite.config"; else echo "(unknown)"; fi`

Listening dev ports: !`out=$(lsof -nP -iTCP:3000-3010 -sTCP:LISTEN 2>/dev/null | head -5); echo "${out:-(none)}"`

## Instructions

**The one rule: every visual claim rests on what the browser rendered and you read.** A diff that reads right, a green build, and a 200 response all stop short of pixels, and a fix claim needs the broken state and the fixed state under the same URL, viewport, and steps. The bar is a report where each claim sits beside the evidence that decides it, with the browser tool, URL, port, and viewport it was measured at, every page that renders a shared component, and what was not checked: open [examples/render-check.md](examples/render-check.md) before reporting, and check the draft against [examples/rejected.md](examples/rejected.md).

Verify the claimed visual state in a real rendered browser with a screenshot or DOM assertion as evidence, manage the dev server lifecycle cleanly, and never kill processes by name.

### Process

1. Parse `$ARGUMENTS` (a route or full URL, `--port <n>`, `--mobile` for a phone viewport; with no arguments, take the target from the conversation instead: a pasted DOM fragment like `[<div class="..."> in Component (at path/file.tsx:85:6)]` names the exact source component and file, a pasted image is the reference state, a localhost URL is the page under test).
2. Read the repository's standing instructions (`AGENTS.md`, `CLAUDE.md`, project memory) for visual QA ownership before opening anything. When they say the user reviews visuals themselves, make the change, start no browser loop, and hand over. When they require asking before opening a browser, ask once.
3. Reuse before building: a server already serving the app when the ports probe shows one listening, a tab already open on it (list the browser tool's tabs before concluding there is no browser, since a missing Playwright install is not a missing browser; seen: a run reported "no browser runner" after probing only Playwright while the session exposed a browser tool), and the repo's own browser harness (Playwright or Cypress suites, Storybook, an Electron debug launch) when one exists, since it already knows startup, auth, and fixtures; otherwise start the dev server. Clear stale dev locks first (for Next.js, remove `.next/dev`, since a stale lock points at a reused PID and breaks startup), then start the dev script with `nohup`, redirect output to a scratch log, and record the PID. Follow [references/browser-loop.md](references/browser-loop.md) for the exact lifecycle commands.
4. Poll readiness with `curl --retry --retry-connrefused` against the expected port, then read the actual port from the log. Frameworks silently shift port when the default is busy (Next.js moves to 3001 on EADDRINUSE), and a hardcoded URL then tests the wrong app. Bound the poll (about 90 seconds); when it expires, stop waiting, capture the log tail as the failure evidence, kill the recorded PID, and report the startup failure instead of retrying past the budget. A run whose sandbox refuses the port or the browser calls follows Unattended runs in [references/browser-loop.md](references/browser-loop.md).
5. Drive the page with the browser tools this session exposes, whichever they are, and search the tool list when they are deferred; never assume one family (seen: the skill named Chrome DevTools tools after the machine had replaced them with another browser tool, and its installed copy was edited by hand to name the new one instead). With several, take the one the standing instructions name, else the one that can emulate a viewport and a color scheme, since step 7's states need both. Open the page where the tool opens it by default, the person's configured browser, and pass a private or isolated target only when the claim is about a signed-out state (seen: a run opened a signed-in check in a private window, and the user asked why it had not opened in their own Chrome). Map each operation through the Browser tools table in [references/browser-loop.md](references/browser-loop.md), and size the viewport to the context the feedback came from; `--mobile` or a phone screenshot as the reference means a phone viewport. With no browser tool and no repo harness, report every visual claim as not checked.
6. Wait for hydration before asserting. Navigation resolves before the app hydrates, so wait 1 to 2 seconds or poll for an app marker inside the same script call that queries the node.
7. Assert the specific claim. Query the exact node (the pasted fragment's file and line locate the component; open that file rather than guessing from class names), take a screenshot and look at it, and judge the result against the ask. Then list the states the change touches (each viewport the surface supports, light and dark, empty, loading, error, and each flag or permission that changes the surface) and check each or mark it not checked with the reason, because one screenshot of one state never closes a run (seen: one screenshot of one viewport, then a claim that the real render was confirmed and a PR).
8. Iterate only when the request authorized fixing. Apply the edit, let hot reload pick it up, re-assert and re-screenshot the same URL at the same viewport, and report with the evidence. A "this fixes X" claim needs both sides: capture the broken state from the pre-change code first (same URL, viewport, and steps), then the fixed state, since an after-only screenshot cannot show that anything changed. A fix to a shared component is re-asserted on every page that renders it, not only the page the feedback named. When the request asked only to look, or a read-only caller composes this skill for evidence, apply no edit: capture the state, report what the screenshots and assertions show, label any change you suggest as not applied, and end with the finding for the caller, naming the cause at its exact `file:line` (seen: a read-only caller's run was told to apply edits).
9. Tear down. Close the tabs or pages this run opened, kill only the recorded PID of the server this skill started, and leave any pre-existing server and tab as they were.

### Rules

- Never `pkill`, `killall`, or kill by process name. Use only the exact PID recorded at startup, and only for a server this skill started.
- A curl 200 proves liveness, not visual correctness; every visual claim carries a screenshot or DOM assertion as evidence.
- Never screenshot-loop in a repository whose standing instructions say the user reviews visuals themselves.
- Never add Playwright or another browser dependency to the project just for this verification; use what is installed or the session's browser tools.
- Never inject DOM or app state to produce the state under test; drive the UI the way a user would, and use state inspection only to confirm what was observed. A script that dispatches an event (a wheel, drag, or key event) is injection too, so a gesture the browser tool cannot perform is reported as not checked (seen: a failed drag was replaced by a scripted wheel event and the zoom was reported as checked).
- In a workspace showing personal or customer data, do not save screenshots or snapshots without the user's agreement.
- Run every browser check through this process, a quick look at localhost and a check another skill composes included; a raw browser tool call, whichever tool provides it, skips the standing-instructions check, the port read, the hydration wait, and the teardown (seen: browser checks in 82 sessions ran through raw browser tools without it).
