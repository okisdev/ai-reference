## Context

Design law in the tree: !`top=$(git rev-parse --show-toplevel 2>/dev/null || pwd); out=$(find "$top" -maxdepth 5 \( -name node_modules -o -name .claude -o -name .git \) -prune -o \( -iname AGENTS.md -o -iname CLAUDE.md -o -iname design.md \) -print 2>/dev/null | xargs grep -liE 'design (contract|law)|type sizes|line budget' 2>/dev/null | head -5); echo "${out:-(none)}"`

Kit, shared, and chart directories: !`out=$(find . -name node_modules -prune -o -type d \( -iname ui -o -iname shared -o -iname charts \) -print 2>/dev/null | grep -v node_modules | head -6); echo "${out:-(none)}"`

Density audit: !`out=$(node "$HOME/.agents/skills/design-dashboard/scripts/density.mjs" . 2>/dev/null | head -24); echo "${out:-(density script unavailable)}"`

Routes: !`n=$(find . -name node_modules -prune -o -name 'page.tsx' -print 2>/dev/null | grep -v node_modules | wc -l | tr -d ' '); echo "$n page.tsx files"`

## Instructions

Decide what the dashboard is for, diagnose it in measurements, draw it in the repository's own law with one contribution per reference, write the blueprint, implement the core first and the pages in waves, verify in a browser, and leave the contract in AGENTS.md at an uncommitted tree.

### Process

1. Parse `$ARGUMENTS` (the app path, default the dashboard app the conversation names; reference paths or URLs the user named as style sources; `--analysis` ends the run at the blueprint, and an analysis-shaped ask does the same without the flag). Compose `onboard-repo` when the app is unfamiliar, and confirm the worktree and branch with `git worktree list` before any edit.
2. Frame the job in one paragraph before touching layout: the audience (internal staff, customers, public), the question each screen answers, and whether the dashboard's job is Decide (queues, approvals, actions) or Read (knowledge the product produced); a surface that is only aggregates is a proof page, never a destination. A product whose value lands elsewhere (in GitHub, in a chat) gets a control surface built for a sixty second visit and a reason to return, never a destination optimized for time on page. When the ask is relayed from a stakeholder, read that person's own words before inferring intent from the prototype, and separate the literal ask from its motivation.
3. Diagnose in measurements, not adjectives. Read the Context density table (rerun `scripts/density.mjs <app-path>` when the app is not the cwd): body size, radius, control and row heights, hand-styled panel count, content widths, shell widths, rules per panel, transition-all and shadow counts. Then the five layers: information architecture, URL state (a copied URL reproduces the view or it does not), page templates, visual language, and duplicated presentation logic. Then the existence review: every view shows real data through a real endpoint to real users, and a view drawn against an endpoint that does not exist or a table that is empty in production is deleted, not restyled. Cite `file:line` for every defect, and name dead chart code and discarded query results as evidence of what an earlier pass removed.
4. Read the law before drawing, in the order [references/contract.md](references/contract.md) gives: the app's own contract, the organization's published law, the organization's own prior blueprints and unwired libraries, a sibling app on the same stack, the brand's surfaces, and only when none exists the reference's application density defaults, which are then written into this repository's contract as its own. Study each named reference through `mirror-reference`, which fixes one contribution per reference as take and not-take and dates its direction from git history; an ambiguous reference name is interpreted out loud in the blueprint's reference table, never asked about first.
5. Fix the structure against the Frame, URL state, Detail grammar, and List grammar rows of [references/contract.md](references/contract.md), and an internal console against [references/console-access.md](references/console-access.md), logging each change as a defect with its `file:line`. Before treating a grouping as wrong, confirm in the browser that its labels render at all; a word that names two things in the app is renamed in the same pass; a public or anonymous view that shows more than the signed-in console is a defect.
6. Decide the content through `plan-charts`: what each page shows, in which form, where, and what production data says it will look like.
7. Write the blueprint as a published artifact in the section order of [references/blueprint.md](references/blueprint.md): wireframes drawn from real data with not-yet-real data seams marked, every fork decided on the spot with its basis, the expected gain quantified (rows per screen, content width, tiles that carry a trend), and the open product decisions batched in one list with a recommendation each. Stop for the user's reply on the blueprint: one reply approves it or delegates the open decisions, and no code changes before it; an analysis ask ends here.
8. Author the core first and alone: tokens, the compact kit exemplars with unchanged prop APIs so call sites do not change, the shared primitives (page shell, section, key/value row, stats grid, entity header, copyable id, filter bar, empty state, confirm dialog), and the contract written into the app's AGENTS.md per the contract reference; typecheck, lint, and format the core before any page changes.
9. Fan out the pages as parallel packages on top of the verified core: one exemplar page first, breadth pages next, detail and trace pages last. Each brief names its files, the exemplar page path, the contract path, sibling packages' files as in flight, and its verification command, and the uncommitted core rides into each worktree as an applied and staged patch. Merge each returned package into the main tree one at a time with a typecheck after each; a package past its lifecycle budget is terminalized as a sizing error and re-dispatched bounded, never waited on; when a package deleted a file mid-rewrite, restore it from the base and re-dispatch a bounded follow-up instead of patching around the gap.
10. Verify in a browser through `verify-ui` in a declared order: the overview, a list with filter, sort, and paging, a detail page, the command palette, a create form, both themes, a narrow viewport, with the console watched throughout; prove an alignment claim with measured pixels, not a glance. Seed staging with realistic variety (many entities, id spellings, outcome mixes) through the app's own seed script or `inspect-db --write` against the staging connection named by host, never production, before judging a list or chart page. Grep for a destructive action outside the confirm dialog and for a hand-rolled control the kit has before calling the pass done. The handoff names the surfaces not verified, each delegated decision with the choice made, and any page that missed its density target with the cause.
11. Run the polish loop on the user's feedback: a pasted bracketed component stack is a locator, resolved to its file and line; fix at the shared component; put labels back when compression reads as broken; when two consecutive instructions contradict, the later one wins and the reading is flagged; a defect that recurs becomes a contract rule on its second occurrence.
12. Leave the contract behind: the design contract and the chart grammar live in the app's AGENTS.md in the shape the contract reference's writing section gives and pass `python3 "$HOME/.agents/skills/normalize-agents-md/scripts/measure.py" <app-path> --strict`, the blueprint link goes to project memory through `use-project-memory`, and the tree stays uncommitted; committing composes `commit-changes`, shipping composes `ship-pr`.

### Rules

- Every hue outside the roles the contract names is a defect; the contract, never this skill, names the roles.
- A category of view is never deleted because one use of it failed; the category is split and each use decided.
- A green typecheck, lint, and build is not visual verification; a primitive migration or shell restyle is done only after every overlay was opened and every migrated custom property was diffed.
- Hidden navigation is a courtesy, never a guard; the data layer enforces access.
