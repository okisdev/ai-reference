# Monitor cycle

Invoked from ship-pr step 4: one idempotent pass per loop tick. Parameterize OWNER and REPO from the Repository probe into every query and never hardcode them; re-fetch fresh state each pass and never cache the head SHA (`gh pr view <n> --json headRefOid`), since after pushing fixes the head moves, review bots re-run, and pending checks or threads clear.

- **Wait set.** The full rollup minus the names the user gave for this PR (`--advisory`, or a named skip during the loop). Required-set discovery, project memory, and earlier sessions do not shrink this set. After `--watch` returns, re-read the rollup and keep watching if anything new is pending.
- **Required set.** Discover the required checks once, taking the first source that yields data: `gh pr checks <n> --required` (exit 0 all passed, 8 some pending, 1 some failed), then ruleset `required_status_checks[].context` via `gh api repos/$OWNER/$REPO/rules/branches/$BASE`, then legacy branch protection contexts; treat a 404 as not protected and a 403 as insufficient scope, both falling through rather than reading as no required checks. From the same ruleset or protection payload read `required_approving_review_count` for the approval gate. This set decides which red items `--admin` still cannot override; it is not a skip list.
- **Check state.** Block on `gh pr checks <n> --watch --fail-fast --interval <seconds>` to wait for the checks to settle without a fixed-cadence wakeup (`--fail-fast` returns on the first red so remediation starts before the rest settle), then read `gh pr view <n> --json statusCheckRollup` to classify, counting only the most recently started run of each check name on the head (an older CANCELLED or failed run that a later run of the same name replaced is history, not a result), normalizing both node shapes (CheckRun `.name` plus `.conclusion`, StatusContext `.context` plus `.state`) into pass (SUCCESS, NEUTRAL, SKIPPED), fail (FAILURE, ERROR, CANCELLED, TIMED_OUT, ACTION_REQUIRED), or pending (keeps looping; pending is not failure). `--watch` only blocks; the rollup is still what classifies pass versus fail. Do not trust the rollup `isRequired` field, unreliable on ruleset repos. Absence from the required set is not a skip. Before fixing a red check in the PR, check whether the failure is unrelated to the PR's diff and the same check is green on the current base; when both hold, update the branch from base and re-watch instead of patching an inherited failure into the PR. When a red run reads as flaky (a known flaky suite, an infra error unrelated to the diff), re-run it once and report both outcomes as the flake evidence; a second red is a real failure, never a second retry, unless its failure matches an open issue that already tracks that flake and touches none of the PR's files: then rerun it, add the hit to that issue, and leave the flake's fix to its own PR (seen: a tracked browser flake hit five times in one day). A review bot's check that ends TIMED_OUT or CANCELLED without posting a review on this head is the bot's infrastructure, not a finding: rerun it once, and when the rerun is refused or ends the same way, drop it like a quiet item and name it in the report.
- **Stale green.** A completed rollup is evidence about the base it ran against, and age alone never makes it stale. Read the newest completion timestamp across the rollup (CheckRun `completedAt`, StatusContext `createdAt`) and the base tip at that time (`gh api -X GET "repos/$OWNER/$REPO/commits" -f sha=$BASE -f until=<timestamp> -f per_page=1 --jq '.[0].sha'`). The green is stale when the files the base changed since (`gh api "repos/$OWNER/$REPO/compare/<base tip then>...$BASE" --jq '[.files[].filename]'`) include a file the PR changes (`gh pr view <n> --json files --jq '[.files[].path]'`). Refresh a stale head (`gh pr update-branch <n>`, or merge the freshened base and push; `but pull` then restack on the GitButler path) and let the new head's checks settle before the gate re-evaluates; a green whose base moved only elsewhere stays as it is.
- **Heartbeat and stall.** Defined once in ship-pr step 3 (the 15-minute settle window, the per-tick heartbeat line and liveness re-check, stall dropping, transient-failure re-entry); apply it unchanged on every tick.
- **Bounded poll.** When the rollup does not cover the wait, or after three consecutive watch failures, poll `gh pr view <n> --json statusCheckRollup,headRefOid,reviews` every 30 seconds, each call under the step 3 SIGTERM wrapper with a 60 second bound (`perl -e '$p=fork or exec @ARGV; $SIG{ALRM}=sub{kill TERM=>$p}; alarm 60; waitpid $p,0; exit($? & 127 ? 124 : $? >> 8)' gh pr view <n> --json statusCheckRollup,headRefOid,reviews`), emit one heartbeat line per poll naming each pending item and its age, classify each result as in Check state and Reviewer states, and end when the awaited items settle or the step 3 budget runs out.
- **Reviewer states.** Reduce `gh pr view <n> --json reviews` to the latest state-changing review per author (APPROVED, CHANGES_REQUESTED, DISMISSED; COMMENTED never changes approval); list any gating reviewer (a human, or a ruleset-required reviewer) still in CHANGES_REQUESTED, and count distinct current APPROVED reviewers against `required_approving_review_count`. Classify bots structurally via `gh api --paginate repos/$OWNER/$REPO/pulls/<n>/reviews` `user.type == "Bot"`, never by login pattern, because a bot that re-reviews every push fills the first page.
- **Review threads.** Run ship-pr's own reviewThreads query (owner and repo parameterized, the number passed with `-F` as a JSON Int) selecting each thread's `id`, `isResolved`, `isOutdated`, and `comments(first: 1){nodes{databaseId}}`, paginating past `first: 100` via `pageInfo.hasNextPage` and `endCursor`; this read drives both resolution (the `id` to resolve, the `databaseId` to reply) and gate condition (2). Delegate only the valid-versus-noise-versus-stale claim classification to `verify-pr-comments`.
- **Merge state.** `gh pr view <n> --json state,mergedAt,mergeable,mergeStateStatus,isDraft`; a MERGED state means the PR merged outside the loop, so stop polling and go to cleanup, and a CLOSED state ends the loop with a report; wait on UNKNOWN; on BEHIND, if ship-pr owns the head branch, update it and re-poll (`gh pr update-branch <n>`, or rebase or merge the freshened base then push; `but pull` then restack on the GitButler path), but if the head is on a fork ship-pr cannot push to, stop watching and report the blocker rather than looping on an update that cannot happen; treat BLOCKED as not-yet-mergeable (a required approval or check still outstanding) and keep polling; and never auto-merge DIRTY, CONFLICTING, or DRAFT. When the owned-branch base update itself conflicts, resolve only the mechanical part: regenerate conflicted lockfiles with the package manager instead of hand-editing, scan for leftover conflict markers, and run the covering checks before pushing; a semantic conflict in source stays a blocker to report, not a resolution to improvise mid-loop. A base under a merge queue answers the merge command by enqueuing the PR (the command says the merge strategy is set by the merge queue), and `gh pr view` has no queue field: read `gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){isInMergeQueue mergeQueueEntry{state position}}}}' -f o=$OWNER -f r=$REPO -F n=<n>`, keep the queued PR as a pending item that names its queue state and position on each tick until MERGED, and report its removal from the queue as the blocker; a queued PR leaves the queue (`dequeuePullRequest`) before a user-passed `--admin` can merge it (seen: `gh pr view` answered `Unknown JSON field: "isInMergeQueue"`, and an admin merge of a queued PR was refused).
- **Idempotency.** A resolved thread is skipped on the next read, so the gh state is the durable record that prevents a later tick from re-replying; resolve before the next tick.
