name: ship-pr
description: Ship a change to a merged PR end to end (ship it, run the flow, merge it), building or resuming the PR, looping over CI and review threads to address feedback, and merging once every check and review has settled on the head that merges.
argument-hint: "[task-or-pr] [--squash|--merge|--rebase] [--approve] [--admin] [--delete-branch] [--base <branch>] [--draft] [--advisory <check>] [--cwd <path>]"

## Instructions

**The one rule: never merge on state you have not watched settle.** Every check finished on this head, every thread resolved, every commit judged by `verify-pr`, and the head you merge is the head you checked. The bar is [examples/run.md](examples/run.md): a named status line on every tick, fixes batched, the gate re-read right before the merge, and the merge confirmed from GitHub; check your run against [examples/rejected.md](examples/rejected.md).

Drive the change to a merged PR: implement if needed, branch, open the PR, then monitor CI and reviews until the merge gate passes, addressing feedback each cycle. Execute immediately without asking.

Delegate branch/commit/PR to their named skills (`create-branch`, `commit-changes`, `create-pr`), apart from the single-purpose review fix that `references/threads.md` commits directly; the should-this-merge judgment to `verify-pr`; review-thread triage to `verify-pr-comments`. Own only the monitor loop, the merge gate, and the merge. Invoke the others by name and act on their output; never inline or reimplement their logic.

Auxiliary skills, used only when relevant:
- **verify-issue**: optional upstream precursor when the change originates from an issue.
- **organize-commits**: optional pre-PR tidy, kept out of the unattended loop because it pauses for confirmation.
- **summarize-review**: when shepherding a contributor's PR rather than ship-pr's own change.
- **approve-pr**: on another author's PR, to post the maintainer approval near the merge gate (condition (3)); it owns the self-approval guard and the `gh pr review` write.

### Process

1. **Detect state and resume at the right step (adaptive entry).** Read the Context probes and resume at the first matching row. The leading positional of `$ARGUMENTS` is a change description, a PR number/URL to resume, or empty (operate on the current branch). Flag semantics that are not obvious from their names: `--advisory <check>` excludes a named check from the wait set (repeatable) but cannot mark a human reviewer skippable; the user naming a check to skip during the loop counts the same for that PR, while a project memory, an earlier session, the required-set membership of a check, or a bot login never adds one; `--cwd <path>` names the repository or task worktree the change lives in when it is not the session's directory: rerun the Context probes there (`git -C <path>`, `gh` run from `<path>`), run every command there, and pass `--cwd <path>` to `create-branch`, `commit-changes`, and `create-pr`, whose own probes otherwise read the session's directory (seen: 145 runs probed the primary checkout instead of the worktree that held the change); `--draft` is a hold short of merge, not a skip; the merge method (`--squash` default, `--merge`, `--rebase`) is validated early against `allowed_merge_methods` (step 3); on another author's PR the approval path in condition (3) runs by default, and `--approve` names that default without changing it; `--admin` applies only when the user passed it in this request (see Merge).

   | Priority | Condition | Action |
   |---|---|---|
   | 1 | `$ARGUMENTS` names a PR number/URL, or Existing PR is a URL | skip the build, enter the monitor loop (step 3), capturing the PR number |
   | 2 | uncommitted changes present | build the PR from branch and commit (step 2, `references/build-pr.md`) |
   | 3 | commits ahead of base but no open PR | build the PR from PR creation (step 2) |
   | 4 | only a task description on a clean tree | build the PR from implement (step 2) |
   | 5 | none of the above | nothing shippable; report and stop |

   Never force the full flow when a PR already exists. Detect GitButler once by comparing Current branch to `gitbutler/workspace` (the create side uses the `but` CLI only there); on that path, and whenever the change lives in another worktree, read `references/checkout-paths.md` (the virtual-branch PR lookup and the step 5 cleanup). Derive OWNER and REPO from the Repository value; for an existing PR prefer its real base via `gh pr view <n> --json baseRefName`.

2. **Build the PR.** To build the PR (implement, branch, commit, changeset, open), follow `references/build-pr.md`; skip this when resuming an existing PR. When resuming an existing PR that is missing a required changeset or documented changelog entry, still add and push it per the step 3 guidance in `references/build-pr.md`.

3. **Monitor by watching gh state, not a fixed clock.** Before the first wait, validate the configured merge method against the repo's `allowed_merge_methods` (`gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed`); if the requested method is not permitted, substitute the closest allowed (prefer squash, then rebase, then merge) and note the substitution rather than discovering the conflict at merge time. Then block on gh's own API-polling watch until the awaited state changes, run one idempotent monitor pass, then block again. The wait set is every rollup check and every in-flight review, including review bots; `--watch` returns when currently registered items settle, so after it returns re-read the rollup and keep watching if anything new is pending. `gh pr checks <n> --watch --interval <seconds>` is the primary wait; `gh run watch <run-id> --exit-status` is the single-run equivalent. Bound every watch call below the shell tool's time limit with a wrapper that sends SIGTERM and exits 124 on expiry (`perl -e '$p=fork or exec @ARGV; $SIG{ALRM}=sub{kill TERM=>$p}; alarm 270; waitpid $p,0; exit($? & 127 ? 124 : $? >> 8)' gh pr checks <n> --watch --interval 30`); a bare `alarm 540; exec` never stops gh, whose Go runtime catches SIGALRM and keeps running (seen: a `gh run watch` outlived its 540 second alarm by 23 minutes). A watch that hits the bound with items still pending is a heartbeat tick, not a failure, so emit the status line and re-enter. When the rollup does not cover the wait, fall back to a short bounded gh poll per `references/monitor.md`. Right after pushing a fix, pause briefly before watching so the new run registers, or `--watch` may return immediately on the previous head's already-settled checks. Every wait is heartbeat-bounded: reviews and CI are expected to settle in about 15 minutes, so keep waiting through that window, including an item that finishes around it; 45 minutes without a settled head bounds the loop unless the user set another, its clock restarting at each push, and from the third fix round on each status line names the round count and what each round fixed (seen: three loops ran past a whole-PR 45 minutes in silence while each push restarted their checks). Emit one visible status line per tick naming each pending item by its exact check or reviewer name, so the user can pass it to `--advisory` verbatim, and its age, before each wait as well as after it, since a line that appears only when a wait returns leaves the user in silence for the whole wait (seen: a user asking to look at CI nine minutes into a 540 second wait); on each tick re-verify the awaited item is alive (its run or reviewer shows activity since the last tick), not merely still pending (seen: users asking to check CI after 5 to 30 silent minutes). A transient API failure (EOF, 5xx) ends the watch command, not the wait: re-enter the watch, and after three consecutive command failures use the bounded poll for the rest of that wait. Drop a still-pending item only when it has gone quiet well past the 15-minute window (no new timestamps across two consecutive ticks and none after one re-fetch of the run), and note it; 15 minutes elapsed with the run still moving is not a skip. A red conclusion never drops, apart from a review bot's timeout under Check state in `references/monitor.md`; a persistent one is the red-check blocker in step 5 even if the check is absent from the repo's required set. No dropped item is ever polled again.

4. **Run each monitor pass** following `references/monitor.md` for the full per-tick mechanics (wait-set and required-set discovery, check and reviewer classification, the reviewThreads read, merge-state handling, idempotency). Call `verify-pr` for the merge-worthiness recommendation on the first pass after creation, then again for every commit that lands afterwards whoever pushed it, passing `--since <last verified head>` so a re-read costs the delta instead of the whole patch. Carry that SHA forward from verify-pr's Verified head line: it is the loop's own state, recorded when a pass returns and replaced only when a later pass supersedes it. Skip ticks where the head has not moved. A verify-pr report never ends the turn: when it says merge as-is and the gate holds, merge in the same turn, and when it lists findings, start the fixes (seen: two ships stopped on "Merge as-is" until the user asked how far along they were). Fix every Blocking and fold-in finding a pass returns in a follow-up commit and push, batching the pushes: while checks or review bots are still running on the current head, commit locally and push once they settle, because each push cancels the in-flight runs and reviews and restarts them; a finding marked follow-up issue stays out of the PR, and a fold-in whose fix outgrows the touched files or fails the PR's checks is backed out and reclassified as one. A fix ship-pr pushed itself still counts, because authoring a commit is not verifying it and the gate's checks establish only that the tree builds.

5. **Merge, then clean up.** When the Merge gate holds, merge per the gate's command and confirm the outcome from `gh pr view <n> --json state,mergedAt` rather than the command's exit code (seen: `--delete-branch` printing a failure after the merge itself succeeded), then take the normal exit. When the shipped branch lived in its own worktree, remove that worktree; on a single checkout, return to the default branch and sync it so the local default carries the squashed merge and the next ship-pr starts clean (`git checkout <default> && git pull --ff-only` on the plain-git path). For a worktree or the GitButler path, follow `references/checkout-paths.md`. Then stop (the only normal exit). A `--draft` PR is a hold: keep watching but never `gh pr ready` or merge it until the user marks it ready. If the gate cannot clear, stop watching and report the blocker, leaving the PR branch checked out and its worktree in place. Blockers:
   - a persistently red check
   - an unmet required approval the condition (3) approval path could not clear, unless the user passed `--admin` and Merge allows it
   - a DIRTY or conflict-blocked BEHIND branch
   - a fork head ship-pr cannot push to
   - an unreachable gating reviewer
   - `verify-pr` recommending close or redirect

   The step 3 budgets bound the loop; treat UNKNOWN merge or check states as still computing and re-poll within them rather than escalate.

### Addressing threads

Disposition and resolve every unresolved thread per `references/threads.md` (the three dispositions, the reply and resolve commands, and the rule against prose that only acknowledges feedback).

### Merge gate

Three conditions, all required, plus the mergeability preconditions; only an explicit user instruction to merge now relaxes them (see Merge now).

- **(1) Every check settled.** The wait set is the full rollup minus the names the user gave for this PR (`--advisory`, or a named skip during the loop); nothing recorded elsewhere shrinks it. Wait for each item to leave pending. Reviews and CI are expected to finish in about 15 minutes; keep waiting through that window, including an item that completes around it. Drop a still-pending item only when it has gone quiet well past the window, and note it; a red conclusion never drops, except a review bot's check that timed out or was cancelled without posting a review on this head, which follows Check state in `references/monitor.md`. A Bot review's check color does not block once that review has posted on this head (condition (2) owns its threads). Every other settled check must be pass (SUCCESS, NEUTRAL, SKIPPED). A pass is also only as current as the base it ran against, but age alone never makes it stale: the green is stale when commits that landed on the base after the newest completion in the rollup touch files the PR changes, and then the head is refreshed per `references/monitor.md` and the fresh run awaited instead of merging on it (seen: checks that completed long before against an old base counted as settled). A green whose base moved only elsewhere stands, because a refresh for age alone cancels the review bots and reruns every check (seen: seven approved PRs were refreshed only because their checks were an hour old, and the user overruled it); a conflict, or a branch the ruleset requires to be up to date, is handled in Merge state. Absence from the repo's required set is not a skip, and a pending review bot is not skippable because it is a bot (seen: merges that went in while a review bot was still running). Discover the required set per `references/monitor.md` only to know which red items `--admin` still cannot override. Never hardcode required checks or a bot name; classify review bots via `user.type == "Bot"` on `gh api --paginate repos/$OWNER/$REPO/pulls/<n>/reviews`.
- **(2) Threads resolved.** Every review thread is resolved (ship-pr's reviewThreads read returns no `isResolved == false`).
- **(3) Reviewers satisfied.** The count of distinct current APPROVED reviewers meets the repo's `required_approving_review_count`, and no GATING reviewer is in CHANGES_REQUESTED (the latest-per-author reduction is empty for humans and required reviewers). Address the feedback and wait for re-approval; never dismiss the review. On another author's PR (the PR author does not match the My login probe), when the only shortfall is a required approval (no GATING reviewer in CHANGES_REQUESTED) with conditions (1) and (2) already holding, delegate to `/approve-pr <n>` (without `--merge`) to post the approval by default, then re-evaluate the gate; approve-pr gates its own write on a fresh verify-pr, so a PR that does not earn the approval comes back as a decline and this gate reports the blocker instead of forcing the merge; a decline only because the base branch would not count this account's approval (it pushed the last commit) falls to a user-passed `--admin` in Merge, and without one it is the blocker. Self-approval is platform-blocked, so on ship-pr's own PR this path never runs; an unmet required approval there waits for a human reviewer or falls to a user-passed `--admin` in Merge.
- **Preconditions.** `mergeable != CONFLICTING`; `mergeStateStatus` is CLEAN, accepting UNSTABLE or BLOCKED only when every non-passing check is a still-pending item dropped after going quiet well past the 15-minute window, a completed Bot-review check whose threads are resolved, or (with a user-passed `--admin`) a review requirement the approval path could not clear, and never DIRTY or DRAFT. When `mergeStateStatus` is UNSTABLE, enumerate every non-passing check in `statusCheckRollup` and confirm each is one of those accepted leftovers before treating UNSTABLE as acceptable; any other non-passing check blocks the merge. A `--draft` PR is a deliberate hold (see step 5). verify-pr supplies only the merge-worthiness recommendation (necessity and correctness, and a verdict of merge rather than close, redirect, or push back); the wait-set classification in conditions (1) to (3) is ship-pr's own per-tick poll.
- **Merge.** When all hold, merge with the configured method, appending `--delete-branch` if requested. A PR that `gh pr view <n> --json state,mergedAt` shows merged outside the loop is done: skip to cleanup in step 5. `--admin` is the user's call, never ship-pr's: append it only when the user passed it in this request, on their own PR to bypass a review requirement that self-approval cannot satisfy, and on another author's PR only after the condition (3) approval path has run and left a requirement an approval cannot clear (a review window, a code-owner rule), naming in the report what it bypassed (seen: `--admin` merged another author's PR past its review requirement when nobody had asked for it). On a base with a merge queue the merge command enqueues the PR, which stays a pending item until the queue merges or removes it (Merge state in `references/monitor.md`); a user-passed `--admin` merges past the queue only within the rule above, and a PR already queued leaves the queue before it can. Immediately before merging, independently re-verify all three conditions and all preconditions, and re-read `headRefOid`; abort and re-run one monitor pass if the head SHA no longer matches the one the gate evaluated. Merge with `--match-head-commit <verified head>`, verify-pr's last Verified head, so GitHub refuses a head that carries a delta verify-pr never judged; when the Verified head sits behind the head about to merge, or the merge is refused for it, run `verify-pr <n> --since <verified head>` and act on it first. Green checks are not cover for that delta, and neither is the commit being ship-pr's own (seen: three of nine merges went in on heads verify-pr never judged, after "I've reviewed every commit up to it myself"). Even with `--admin`, this re-verification still runs: `--admin` may force past a BLOCKED or UNSTABLE state whose sole cause is a review requirement the approval path could not clear or a still-pending item dropped after going quiet well past the 15-minute window; it never overrides a red non-review check, a still-moving pending item, a stale green (condition (1)), an unresolved thread, a CHANGES_REQUESTED review, or a CONFLICTING, DIRTY, or DRAFT PR.
- **Merge now.** An explicit instruction from the user to merge this PR now replaces conditions (1) and (2), the preconditions' limits on UNSTABLE and BLOCKED, and the re-verification in Merge: re-read the head, merge at once, and report every check still pending or red and every thread still open. It still never merges a CONFLICTING, DIRTY, or DRAFT PR, adds `--admin` only within the rule in Merge, and reports a merge GitHub refuses as the blocker instead of forcing it.

### Rules

- No trace of tooling in anything posted under the user's name: no `Co-Authored-By` trailer naming a coding tool, no generated-by line, no session link (seen: tool trailers and session links the user had to strip from merged PRs).
- Commit and push all uncommitted work, including the changeset, before PR creation; never let create-pr open a PR over a dirty tree.
- One branch per change group, where a change group is what the user asked to ship together (a named batch or wave is one PR unless the user splits it); never touch another agent's branch or staged work.
- With several PRs in one request, watch each PR on its own, emit one status block per tick naming every PR, and merge each as soon as its own gate holds; hold a ready PR only for a PR its branch depends on, and refresh that dependent only after its parent merges (seen: ready PRs waited on a sibling's checks until the user asked for separate watches so they could ship staggered).
- Status lines, questions, and the final report use the language of the user's request.
